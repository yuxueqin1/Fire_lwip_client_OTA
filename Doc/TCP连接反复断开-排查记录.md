# 通信板 TCP 连接反复断开 —— 排查记录

> 场景：15-2 代通信板，从机模式（RS485-7 拨码 = Slave），6 路端口全部配置 0 个采集盒
> 记录日期：2026-10-11
> 涉及代码：`User/client.c`（TCP 客户端）、`User/arch/sys_arch.c`、`LwIP/core/tcp.c`、
> `User/task_rs485_7.c`（工作灯 / IO 模块）

---

## 0. 结论速览

**连接是上位机主动断的，断的节奏也是上位机定的。**

- 板子到 `192.168.1.88:502` 的连接，**每 6.5 ~ 7.7 s 被上位机 abort 一次（RST，无 FIN）**；
- 板子收到 RST 后 **固定延迟 1 s 重连**（`User/client.c:756`，没有退避），
  **重连成功的瞬间又无条件申请一次配置**（`User/client.c:671`）；
- 于是现场看到的就是"板子一直在请求配置、上位机也一直在回配置"，
  而 **请求间隔 7.5 ~ 8.7 s = 连接寿命(6.5~7.7 s) + 1 s 重连延迟**；
- `s_work_light`（DO0）闪烁 = `client_is_connected()` 在断/连之间跳，是上面这条的直接结果，
  不是另一个独立故障。

**板子这一侧已经查干净**：没有主动断开的代码路径、没有复位过、没有异常数据外发、
配置长度/结构与上位机严格一致。

**剩下的问题只在上位机那侧**：它为什么每 ~7 s 断一次。三条候选假设与分辨方法见 §5。

## 2. 抓包数据（已过滤 `ip.dst == 从机板`）

```
502→50177 [PSH,ACK] seq=463 ack=12 win=64229 len=4      心跳 00 A5 00 00
502→50177 [PSH,ACK] seq=467 ack=12 win=64229 len=8      校时 00 A3 04 00 5c 36 cb 6a
192.168.1.99→:50179 [RST,ACK] seq=1 ack=1 len=0         ← OTA 探测，正常（§6）
502→50180 [SYN,ACK] seq=0 ack=1 win=64240 MSS=1460      ← 板子新连接（新源端口）
502→50180 [PSH,ACK] seq=1   ack=12 len=8                校时
192.168.1.99→:50181 [RST,ACK]                           ← OTA 探测
502→50180 [PSH,ACK] seq=9   ack=12 len=454              ★ 配置帧 = 4B 帧头 + 450B 数据
502→50180 [PSH,ACK] seq=463 ack=12 len=4                心跳
192.168.1.99→:50182 [RST,ACK]                           ← OTA 探测
502→50180 [PSH,ACK] seq=467 ack=12 len=4                心跳
192.168.1.99→:50183 [RST,ACK]                           ← OTA 探测
502→50180 [RST,ACK] seq=471 ack=12 win=0 len=0           ★ 上位机 abort 掉这条连接
502→50184 [SYN,ACK] ...                                 ← 板子 1 s 后重连（又是新源端口）
502→50184 [PSH,ACK] seq=1 ack=12 len=8                  校时 …… 循环
```

**这段抓包能直接读出来的三件事：**

1. `ack=12` **从头到尾没变过** —— 说明板子在这整条连接里**只发出过 11 字节**，
   即申请配置帧（`User/client.c:147-149`），之后**一个字都没再发**。
2. `seq=471` 那个 RST **紧接在上位机自己刚发完的 4 字节包后面**（463+4=467，467+4=471），
   而且 `ack` 没变、`win=0` —— 这是**上位机应用层自己 abort 掉这条连接**的指纹，
   不是"收到了什么怪包才回的 RST"。
3. 源端口 `50177 → 50180 → 50184` 一路递增，中间夹着的 `50179/50181/50182/50183`
   是 `192.168.1.99` 的 OTA 探测 —— **两股连接共用同一个 lwIP 端口计数器**，见 §6。

## 3. 从代码直接得出的结论

### 3.1 "一直在请求配置" ≠ "配置没被接受"

`User/client.c:671`：**TCP 连接一旦建立成功，就无条件发一次申请配置帧** ——
不看 `download_flag`，也不管上一次配置是否已经生效。

所以只要连接在反复重建，抓包上就**永远**是"板子一直在请求配置、上位机一直在回配置"。
这句话本身**不能**作为"配置被丢弃"的证据。真正的现象是：**连接在反复断。**

### 3.2 请求间隔 7.5~8.7 s 是怎么来的（两条算式）

**算式一 · 重试定时器 ≈ 11.0 s，且不换源端口**

`User/client.c:733-744` 的重试定时器，每 `CONFIG_REQ_RETRY_INTERVAL`(=100) 圈重发一次请求。
一圈 = `netconn_recv` 接收超时 + `vTaskDelay(10ms)`（`User/client.c:746`）：

- 接收超时确实是 100 ms：`User/client.c:646` 是 `netconn_set_recvtimeout(tcp_conn, 100)`，
  而 `User/arch/sys_arch.c:396` 是 `wait_tick = timeout / portTICK_PERIOD_MS`，
  `User/FreeRTOSConfig.h:141` 的 `configTICK_RATE_HZ` 是 1000 ⇒ 1 tick = 1 ms，100 ms 就是 100 ms；
- 所以一圈 ≈ 100 + 10 = 110 ms，
  **100 圈 ≈ 11.0 s**；
- 而且它是在**同一条连接上**重发 —— 源端口不会变。

**算式二 · 观测值比它更短，而且每次请求都换源端口**

实测 7.5 ~ 8.7 s < 11.0 s，且源端口一直在变 ⇒
**这些请求不是重试定时器发的**（定时器要 11 s、且不换端口），
而是 `User/client.c:671` 的"连接成功即请求"。

⇒ **连接寿命 ≈ 7.5~8.7 s − 1 s（固定重连延迟）= 6.5 ~ 7.7 s。**
8.7 − 7.5 = 1.2 s 的抖动，就是上位机那次 abort 的时刻在飘。

### 3.3 源端口 = 上电以来开过的 TCP 连接数（这一条很有用）

lwIP 的本地端口是个**纯递增计数器**，而且是 `static`：

- `LwIP/core/tcp.c:159`：`static u16_t tcp_port = TCP_LOCAL_PORT_RANGE_START;`（= 0xc000 = 49152）
- `LwIP/core/tcp.c:1011-1034`：每次分配 `tcp_port++`，到 0xFFFF 才绕回 49152

**推论（两条，都好用）：**

1. **源端口 − 49152 = 板子"上次上电以来"一共开了多少个 TCP 连接。**
   本次抓到 50177 ⇒ 已经开了 **1025 个连接**。
2. **板子一旦复位，计数器会重新从 49153 开始**（它是初值在 .data 里的静态变量，
   复位后 C 启动代码会重新初始化）。
   抓包里是 50177 → 50184 **一路递增、中间没有跳回 49153 附近** ⇒
   **这段时间里板子没有复位过。**

⇒ "板子被软复位 → 配置丢失 → 再要配置"这条**复位死循环**可以排除。

**上电时长估算**：客户端每 ~8 s 开一条 + OTA 任务每 3 s 开一条
（`User/ota/ota_client.c:443`、`User/ota/ota_config.h:107`），
1025 ÷ (1/8 + 1/3) ≈ **37 分钟**。
拿抓包时板子实际开了多久对一下，可以验证这个模型。

### 3.4 板子侧没有"主动断开"的代码路径

- `client_disconnect()`（`User/client.c:212`）**全工程没有任何地方调用**；
- `netconn_close()` 只在重连路径里（`User/client.c:753`）。

⇒ **断开的发起方只可能是对端**，板子只是被动重连。

### 3.5 板子全程只发出 11 字节，心跳"只收不回"

上位机的 `ack` 从头到尾停在 12（= 收到 11 字节），说明板子除了那一个申请配置帧之外
**再没往外发过任何东西**。

心跳处理（`User/client.c:604-608`）也只是把 `heartbeat` 计数器清零，**不回任何东西**。
这在 §5.1 里是最值得怀疑的一处"固件 ↔ 第三方上位机"协议缺口。

## 5. 待验证：上位机为什么每 ~7 s abort 一次

三个候选，都需要上位机那侧或抓包回答。**优先级从高到低。**

### 5.1 上位机在等板子回一个应答（最可疑）

板子在整条连接里只发出 11 字节，之后完全沉默（§3.5）。
如果上位机的服务端对心跳（或对配置）**期待一个应用层应答**，
它永远等不到，等到超时就 abort —— 时间、方向、RST 形态全都对得上。

**抓包上怎么分辨**：量一下 **RST 的时刻距离"上位机最后一次发心跳"多久**。
- 固定 ~7 s ⇒ 就是"等应答超时"，坐实这条；
- 距离**连接建立**固定 ~7 s ⇒ 是"会话时长到点"，与心跳无关（转 5.3）。

**同时要问上位机那边**：你们的服务端在等板子回什么？期望什么格式？

### 5.2 上位机一次只服务一个客户端（两块板子互抢）

现场有主机板 + 从机板两块板子。如果它们**都**连到 `192.168.1.88:502`，
而上位机的软件一次只 accept 一个连接，就是"谁新连上服务谁、把老连接踢掉"，
两块板子互相抢。

⚠ 注意：仓库里的参照实现 `PC_Server/board_server.py`（已从工作区删除，
可取回：`git show HEAD:PC_Server/board_server.py`）**正是"一次只接受一个客户端"**的结构。

**抓包上怎么分辨**（用现有 pcap 就能做）：
1. Wireshark → Statistics → Conversations → TCP，看 `192.168.1.88:502` 上
   **同时有几个不同的客户端**；
2. 看每次上位机发 RST 的那一刻，**是不是紧跟着另一块板子的 SYN / 数据**。

**决定性实验**：把主机板断电，只留从机板，看这条连接还断不断。

### 5.3 固定的会话时长 / "客户端无数据"空闲超时

RST 前没有 FIN ⇒ 是**应用层 abort**，不是优雅关闭。
（Windows 上 `closesocket()` 时若接收缓冲里还有没被应用读走的数据，发出的就是 RST 而不是 FIN。）

现在 6 个端口都是 0 采集盒，板子**除了那 11 字节请求之外对外一个字都不发**，
在上位机看来就是个"连上来只说一句话就永远沉默"的客户端。
如果它的服务端有会话时长或空闲超时，到点就会关掉。

**抓包上怎么分辨**：连接寿命是不是**很稳定地固定在某个秒数**。
- 固定值 ⇒ 超时（5.1 或 5.3）；
- 忽长忽短、且和另一块板子的动作相关 ⇒ 5.2。

## 6. 为什么 `192.168.1.99` 的 `[RST,ACK]` 是正常的

`192.168.1.99:5002` 是 OTA 服务器（`User/ota/ota_config.h:95-96`）。
OTA 任务每 3 s 去敲一次（`OTA_RECONNECT_INTERVAL`，`User/ota/ota_config.h:107`，
用法见 `User/ota/ota_client.c:443`）。现场没开升级工具 ⇒ 没人监听 5002 ⇒ 被回 RST。

**这是预期行为，与本次问题无关。**

顺带它解释了抓包里一个容易看花眼的点：**OTA 任务和 TCP 客户端共用同一个 lwIP
端口计数器**，所以两股连接在抓包里是**交织**在一起的，端口号连成一串
（50177/50179/50180/50181/…）。分析时按**目的端口**（502 vs 5002）分开看。

## 10. 一句话复盘

板子这一侧**没有任何"断"的动作** —— 没有主动断开路径、没有复位、没有异常数据外发、
配置长度与结构严格匹配。断是上位机发的，节奏（6.5~7.7 s）也是上位机定的。

要往下走，只能去问上位机那侧三件事：
**它对一条连接最长保持多久、它在等板子回什么、它一次服务几个客户端。**
