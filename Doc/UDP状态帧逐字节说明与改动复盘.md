## 一、今天（2026-10-13）改了什么

### 0. 一句话

今天从 **v36 一路改到 v42**，看着是 7 个版本，其实只追一条线：

> 现场"两块板偶尔报警、蜂鸣器响 1~2 秒又自己好了" → 要抓这一下 → 帧一路加长 →
> 顺出来"**板子每 36 秒自己复位一次，复位码 31**" → 现在只差"OTA 任务到底卡在哪一步"。

**下班时的状态**：板子上跑的是 **v41**（17:46 实测：`WTD_RESET=31`、上电 34s、同一帧里 5 路端口
全在线）。v42 的映像已经编好躺在 `Output/ota/`，当晚又追加了一版 **v43**（上电假报警的修复）——
明天烧 **v43** 上去，一次拿到两样东西：复位码 31 的成因（v42 的 OTA 诊断帧）+ 上电假报警的消失。

> 补充：今晚复核过一遍 —— 用当前工作区重编 LwIP_A，产物与 `Output/ota/YH-F429_v1.1.0.42_A.bin`
> **逐字节一致**（md5 `cc22b303…`），所以这两个 v42 映像明天可以直接烧，不会有"源码比映像新"的问题。

> 再补充（当晚追加）：**随后又出了一版 v43**（22:59）—— `link_mask` 的初值由"全离线"改成"全在线"，
> **上电不再假报警**，顺带把"偶尔亮响 1~2 秒"的抖动报警也一起修掉了（见 §1.5）。

> 第三次追加（当晚 23:2x）：**v43 的代价不能接受，又改了一版 v44** —— 离线判定从
> "连续 5 轮失败"改成"**距上次成功通信 ≥2s**"（见 §1.6）。帧形状一个字节都没动。

> 第四次追加（当晚 23:5x）：**v44 的"判决那一刻就立刻上报"被撤回，又改了一版 v45** ——
> 要求上位机的模块报警与串口7 的 IO 模块报警**知情同步**，不允许出现"蜂鸣器/报警灯已经
> 响了亮了，而上位机上还一切正常"；顺带把 IO 模块 DI 的超时从 15s 收到 5s（见 §1.6b）。
> **明天要烧的是 v45。**

> 第五次追加（次日）：**v45 烧进去，复位码 31 照旧**——7 连帧抓包坐实了"OTA 任务被饿死"
> 这一支：`report_cnt` / `loop_cnt` / `test1_cnt` 三个计数器**同时冻住不动**（见 §7 第 1 项），
> 而 `stage` 停在 1、`sock_open` 为 0 —— 不是卡在某个调用里，是整个 OTA 任务拿不到 CPU。
> 根因定位到 Modbus 侧 `eMBMReadInputRegisters()` 里 `HAL_Delay(1)` 是**纯自旋、不让出**，
> 6 个 prio 5 的端口任务因此几乎 100% 就绪；prio 4 的 OTA 任务被永久压在下面。
> **处置：OTA 任务优先级 4 → 5，出 v46。烧进去后不再复位。**

> 为什么提到 5 就够（不需要更高）：`FreeRTOSConfig.h` 里 `configUSE_PREEMPTION 1` +
> `configUSE_TIME_SLICING 1`，**同优先级就绪任务按 1ms 节拍轮转**。提到 5 之后 OTA 任务
> 和 6 个端口任务进同一个轮转队列，每毫秒都能分到自己的时间片，30s 的存活窗口内必然
> 能完成若干次上报——它不需要抢在端口前面，只需要"排得上队"。
>
> ⚠ 这是**治标不是根治**：`HAL_Delay` 自旋还在，CPU 依旧被端口任务占满。
> ①②③ 见 §7 第 1/2 项与新增的"根因未清"一栏。

> 第六次追加（2026-10-14，收敛）：**问题闭环，出发布版 v48** —— 把这轮排查堆起来的
> 调试件全部关掉（**代码一行没删**）。详见下面的"§0 发布版处置"。

### 3. 复位码体系收紧（v40，这条最容易踩坑）

原来数据帧（实时帧 / 计轴 / 直流3线 / 曲线）带的是 `19` 和 `20 + port×6`（= 20/26/32/38/44/50）
以及 `3 + n×2` 这些**没登记在文档里**的码，含义是"某帧发送失败"——
结果就是**上位机那边链路抖一下，板子直接整机复位**。更糟的是 `20 + 1×6 = 26`
和"串口任务6卡死"的码 `21+5 = 26` **撞号**，抓到一个 26 都不知道该往哪查。

v40 之后：

* **数据帧/曲线帧一律传 `0U`** —— 发送失败只断链重连（软恢复），不整机复位；
* 复位码只留给"**能定位到具体故障源**"的帧/任务：`1 配置变更`、`2 上位机软复位`、
  `21~26 串口任务卡死`、`27 心跳超时`、`28 TCP发送任务卡死`、`29 申请配置帧发送失败`、
  `30 日志帧发送失败`、`31 OTA任务卡死`；
* **废弃**：`19`、`20+port×6`、`3+n×2`（新固件不会再出现；老固件和旧抓包里还会见到，
  收端工具里标成"v40 起不会再出现"）。

完整表见 §2.5。

### 5. v43：`link_mask` 改成"乐观初值"（上电不报警 + 顺手修掉抖动报警）

**要解决的问题**：上电时端口任务要等配置下发才开始，而配置一生效 `expected_mask` 就变成全 1
（`(1<<SlaveModuelNum)-1`），这时的链路掩码却还是 0，第一轮又要 n × 500ms 才跑完 ——
这段空窗里串口7 的报警判决一直判"整路离线"，于是**上电必报警、蜂鸣器响一阵**，
可实际上一次通信都还没做过。抓到的就是那些 `uptime` 只有 3~6 秒、某个端口
（通常是 12 台模块的 port4）`link = 0` 的帧。

**改法**（都在 [main.c](../User/main.c)）：

1. 新增 `uart_all_online_link_mask(port_idx)` = `(1 << SlaveModuelNum) - 1`，与串口7 的
   `expected_mask` 同一个口径；
2. 端口任务拿到配置（`uart_wait_until_configured()` 返回）时，立刻把这个值同时写进
   `runtime.link_mask` 和**对外发布的** `SerialDataBuf[port][7..10]` —— 这是"上电不报警"的关键，
   因为报警判决读的是后者；
3. 四个端口处理器每轮开头由 `runtime->link_mask = 0` 改成 `= uart_all_online_link_mask(...)`：
   先假设全在线，逐台轮询，**连续失败（`module_error > 3`，也就是第 5 轮）才把那一位清 0**。

**顺带修掉的**：原来"单次丢应答"就会把该位清 0（轮首清 0、失败时不再置位），于是总线上抖一下
→ 一位变 0 → `link != expected` → 报警灯/蜂鸣器亮响一轮（1~2 秒）→ 下一轮自己好。
这正是今天追了一整天的"偶尔亮响 1~2 秒"。改完后 `link_mask` 是**去抖后**的结果。

**代价（要知道）**：真离线的模块也要连续 5 轮才报出来 —— 12 台模块的端口一轮 ≈ 6s，
所以最坏 ≈30s 才报"这台离线"。**这条代价当晚就被判定不可接受，v44 把判决换掉了（见 §1.6）**，
下面这段"想改快慢"的说法也随之作废：

> ~~想改快慢就动这一处：四个 `*_offline()` 里的 `module_error[module_idx] > 3U`。
> ⚠ `uart_module_should_poll()` 的跳过态门限是 `module_error >= 3`，两个阈值是配套的。~~

（v44 起 `module_error` 只剩"什么时候省下等待应答的时间"这一个用途，不再参与离线判决。）

**另一个顺带效果**：`uart_check_port_error_and_arm()` 把"发布掩码 == 0"当成"全部从机离线"，
会在上电时反复重新初始化串口 —— 那个空窗现在也是全在线了，所以上电不再无谓地重初始化串口。

**乐观初值必须配的一个补丁**（别忘了它为什么在）：Modbus 主站端口如果串口初始化失败
（`xMBMaster == NULL`），`uart_process_modbus_master()` 会直接 return，**一轮都不会跑，也就永远不发布结果**——
配上乐观初值，这个端口就会一直显示"全部在线"，把一个坏端口藏起来。所以那里加了一句：
xMBMaster 为 NULL 时**显式按"全部离线"发布**（`link_mask = 0` 并写回 `SerialDataBuf`），
让"端口起不来"这种故障照样报出来。

**验证情况**：0 Error(s), 5 Warning(s)（与改动前同一批告警，无新增）；v43 映像 A 115568 B /
B 115560 B，production.hex 合并自检 PASS、CRC32 `0x7329654E`。
**上机验证要等明天** —— 这版改的是上电和离线判定的时序，只有真板子能验。

### 6. v44：离线判决从"数轮数"改成"看静默时长"（真离线 ≤5s 可见）

**要解决的问题**：v43 的去抖是"**连续 5 轮**失败"，可"一轮"的长度随掉线台数暴涨 ——
一轮里每台**掉线**模块都要白等一个应答超时（Modbus 端口 500ms，库默认；直流3对线 600ms，
盒子手册标称动态响应 ≤250ms 留的 2 倍余量），而每台**在线**模块只要 20~40ms：

| 一个端口里掉线台数 | 一轮大致耗时 |
|---|---|
| 0~1 台 | 仍被补齐到 1s（`UART_POLL_PERIOD_MS` 目标周期） |
| 6 台 | ≈3~4s |
| 13 台（全掉） | ≈6.5s |

于是"5 轮"在 1 台掉线时是 5s，在 13 台全掉线时是 **33s** —— 现场不可接受。

**新规则**（[bsp_rs485.h](../User/usart/bsp_rs485.h) 定门限，[main.c](../User/main.c) 判决）：

1. **判离线只看一条**：距上次成功通信 ≥ `UART_MODULE_OFFLINE_MS`（默认 **2000ms**）→ 判离线
   （`uart_module_check_offline()`，四种端口类型共用）；不再数"失败了几轮"。
2. **去抖照样有**：单次丢应答留下的静默就是 1 个轮询周期（≈1s），够不到 2s → **不报警**；
   连续两轮都答不上（≈2s）才报 —— 现场"报警亮响 1~2 秒又自己好"的抖动仍然被挡在外面。
3. ~~**判决那一刻立即上报**（把 `link_mask` 回写 `SerialDataBuf[port][7..10]`）~~ ——
   **v45 已撤回**：判决当场不再回写，对外发布回到"每轮末尾一次"。原因是立即上报会让
   串口7 抢在上位机的模块数据帧之前点灯/响蜂鸣器（见 §1.6b）。
4. **轮初初值**改成 `uart_round_initial_link_mask()` = 乐观全在线 **减去已判离线的位**
   （`module_offline[]` 是**粘性**标志，只有该台通信成功才清）。这样轮询进行中还没轮到的模块
   只能沿用上一轮结论，轮内的 `runtime->link_mask` 始终是完整的（不是"靠后的模块被随机判
   离线"那种半成品），轮末照原样把它发布出去即可。
5. **起步宽限**：端口任务拿到配置时把每台的 `module_last_ok_ms` 都置成"此刻"，所以从开始轮询到
   最早可能判离线之间至少还有一个 2000ms，首轮偶发一次没答上不会报警（上电不假报警不变）。
6. `module_error[]` **保留原语义**（连续 `UART_MODULE_SKIP_ERR`=3 次失败后进跳过态、每 10 轮探一次），
   只是**不再参与离线判决**。两者故意解耦：跳过态计数的迭代（含跳过轮的累加）既不会让离线上报变快，
   也不会让它变慢。

**预期时刻表（上位机看到那一变的时间）**：

| 场景 | 判定/可见时刻 | 说明 |
|---|---|---|
| **单台真离线**（13 台的口，其余在线） | **≈2~2.5s** | 轮 ≈1s：第 1 次失败的静默 ≈1s 不够；第 2 次 ≈2s 达标，判决即上报 |
| 单次丢应答（总线抖一下） | **不报** | 静默 ≈1s < 2s，该位不动 |
| 连续两轮没答上（真断了 ≈2s） | ≈2s 报；恢复后下一轮自动清 | 真断了 2 秒，该报 |
| 2~3 台同时掉 | ≈2.5~3.5s | |
| 6 台同时掉 | ≈4~5s | 慢轮（判决条件满足后最多再等本轮走完才发布） |
| **整路 13 台同时掉** | **≈6.5s** | 受"一轮扫底 = 13 × 应答超时"这一物理下限限制。这时已是整路故障（数据帧整片 0xFFFF、端口级也报），要压到 5s 内只能缩短该端口类型的应答超时 —— 而 600ms 那个是盒子手册 ≤250ms 留的 2 倍余量，**没敢动**（动它属于改总线时序，要现场验证） |

**关于"判决那一下能不能立刻回写 `SerialDataBuf[7..10]`"**：v43 之前这是**绝对禁止**的（老注释警告的正是这个）——
那时轮首把 `link_mask` 清 0，轮内它是"已判过的半成品"，尚未轮到的模块位全是 0，一回写就会把正常模块误报离线。
v44 把轮初初值改成"乐观全在线 − 已判离线位"之后，轮内掩码的含义变成"未轮到的沿用上一轮结论、
已轮到的用本轮结论"，**完整可信**，技术上可以随时回写 —— **但 v45 又把它撤回了**：立即回写会让串口7
先于点灯/响蜂鸣器，而上位机那一轮的数据帧还没发出去，就是"本地报警、上位机还正常"的错位。见 §1.6b。
⚠ 以后谁再动轮初初值，轮内掩码完整性与"什么时候对外发布"这两件事要一起想。

**想改快慢就动这一处**：`UART_MODULE_OFFLINE_MS`（[bsp_rs485.h](../User/usart/bsp_rs485.h)）。
调大更钝、更慢，调小更快 —— 但**别小于一个轮询周期（1s）**，否则单次丢应答又会被当成离线，
抖动报警会回来。要改跳过态节奏就动 `UART_MODULE_SKIP_ERR` / `UART_MODULE_ERR_SAT`（与判决无关）。

**验证情况**：0 Error(s), 11 Warning(s) —— main.c 的 5 条是**老告警**，另外 6 条是
`bsp_rs485.c` / `client.c` 这次被重新编译后露出来的**历史遗留**（`memcpy declared implicitly`，这两个文件
没包 `<string.h>`；返回值没被用到，实际无影响），与本次改动无关。
v44 映像 A **115800 B** / B **115792 B**（比 v43 各 +232 B），production.hex 自检 PASS、CRC32 `0x69A0452C`。
**上机验证要等明天**：拔掉一台模块掐表看上位机几秒内变离线（期望 ≈2s）；
再让总线抖一下，确认不会误报。

### 6b. v45：撤回"判决当场发布"（上位机与串口7 报警知情同步）+ IO 模块 DI 超时 15s → 5s

**问题 1：串口7 的蜂鸣器/报警灯可能抢在上位机前面。**

v44 为了把"真离线 ≤5s 可见"做实，让 `uart_module_check_offline()` 在判决的那一刻就把 `link_mask`
回写 `SerialDataBuf[port][7..10]`。但这两条消费路径的**节奏不一样**：

| 谁 | 怎么拿 `link_mask` | 什么时候 |
|---|---|---|
| 上位机 | 端口任务每**轮**末尾发一次模块数据帧（`uart_flush_realtime_frame` / `client_add_to_tcp_send_buf`） | 一轮一次 |
| 串口7 的蜂鸣器/报警灯 | 每 **500ms** 读一次 `SerialDataBuf[port][7..10]`（`compute_local_board_alarm()`）后进真值表 | 500ms 一次 |

判决发生在**轮中间**，于是串口7 可能在 ≤500ms 内就点灯响蜂鸣器，而上位机那台的模块数据帧要等本轮走完
才发出去 —— 就是**"本地已经报警了，上位机上还一切正常"**。现场不接受这种错位：蜂鸣器一响，上位机
必须**同时**看得出来。

**改法**：`uart_module_check_offline()` 里那句回写**删掉**，对外发布**收回"每轮末尾一次"**
（各端口处理函数结尾那一句 `*((uint32_t *)&SerialDataBuf[...][7]) = runtime->link_mask;`）。
轮内的 `runtime->link_mask` 照旧实时变（那是端口任务的内部状态），只是不对外。
这样上位机的模块数据帧和串口7 的报警判决都以**轮**为发布边界，**同一轮里一起变**。

> 代价：判决到上位机可见，多了"本轮剩余时间"这一截（最多一个轮长）。单台真离线仍是
> **≈2~3.5s**，离 5s 的要求还有余量；整路 13 台同时掉本来就是 6.5s 的扫底时间，不受影响。
> `runtime->link_mask` 的实时性没有丢 —— `module_offline[]`（粘性离线标志）仍在判决那刻置位，
> 轮初初值照旧把已判离线的位保持 0，所以轮内掩码依然不是"半成品"。

**问题 2：IO 模块 DI 超时 15s 太长。**

`RS485_7_IO_DI_TIMEOUT_MS` 是"连续这么久没有一次成功的 FC02 读 DI，就把过期的 cut/break 按 0
参与真值表"（文档 5.4 的 time_ok 保护）。15s 太长 —— IO 模块一断，最后一次读到的 `break=1`
还能让报警多响十几秒。**改成 5000U**：断线后 ≈5s（实测 5~7s，因为每次失败的 FC02 自己最多阻塞
2s）由 DI 导出的报警就被清掉。抖动余量够：单次 FC02 超时后下一轮成功读会立刻刷新时基，偶发一次
超时不会清报警；连续两次读不到（≈4~5s）本来就该清。

> ⚠ 这条**只影响串口7 自己读 IO 模块的那条链路**（`cut`/`break`），不影响端口模块的离线判决，
> 也不影响工作灯（工作灯仍只看 `client_is_connected()`）。

**验证情况**：0 Error(s), 11 Warning(s)（与 v44 同一批，无新增）。
v45 映像 A **115784 B** / B **115776 B**（比 v44 各 −16 B，删掉一句 4 字节回写），
production.hex 自检 PASS、CRC32 `0xA613C1CD`。
**上机验证要等明天**：拔一台模块掐表（上位机 ≈2~3.5s 内变 0，**同时**蜂鸣器/报警灯响，
不应该有先后）；拔掉 IO 模块，≈5s 内由它导出的报警应消失。

## 二、89 字节状态帧（magic `00 A6 6A 88 99`）逐字节说明

发端：[User/task_rs485_7.c](../User/task_rs485_7.c) 的 `dbg_log_udp_send()` →
`192.168.1.88:50000`；收端工具：[PC_Server/udp_status_log_listen.py](../PC_Server/udp_status_log_listen.py)。

### 2.1 帧长不固定，靠 UDP 报文长度定界

帧里**没有长度字段**，收端只能靠"UDP 报文长度"反推端口块个数 n：

```
总长 = 15 + 13×n + 4 + n = 19 + 14×n      （n = 配了采集盒的端口数，0..6）
```

| n（配了采集盒的端口数） | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| 帧总长（字节） | 19 | 33 | 47 | 61 | 75 | **89** | 103 |

现场这块板 6 路里配了 5 路采集盒，所以是 89 字节。**只有 `[配了采集盒的端口]` 才占端口块和帧尾那一个字节**
（判据：`PortType != DISABLED/SLAVE` 且 `SlaveModuelNum > 0`）。

设计上刻意把**所有诊断量都放在帧尾**，所以：

* `[0..13]` 的偏移永远不变；
* 第 k 个端口块永远从 `15 + 13k` 开始；
* 加新版诊断量只会让帧变长，老收端至少不会错位。

### 2.2 逐字节（下表就是今天抓到的那个 89 字节帧本身）

| 偏移 | 原始值 | 字段 | 该帧的值 | 含义 |
|---|---|---|---|---|
| [0] | `00` | 同步字 | | magic 第1字节 |
| [1] | `A6` | 同步字 | | magic 第2字节 |
| [2] | `6A` | 同步字 | | magic 第3字节 |
| [3] | `88` | 同步字 | | magic 第4字节 |

### 2.3 三个位图怎么读 —— 还有那个"差一拍"的坑

| 字段 | 谁填的 | 含义 |
|---|---|---|
| `expected_mask` | `compute_local_board_alarm()` | `(1 << SlaveModuelNum) - 1`，即"这个端口应该有几台" |
| `link_mask` | 端口任务每轮**跑完**回写 `SerialDataBuf[port][7..10]` | **上一整轮**的在线位图 |
| `kgl_alarm_mask` | `~ALARM_TEMP[port] & link_mask` | 只对**在线**模块判 KGL 开关量报警 |

判读口径：

```
expected & ~link   →  这几位【离线】（维度1）
kgl_alarm_mask     →  这几位【KGL 报警】（维度2）
两者都为 0          →  这个端口干净
```

**⚠ 最容易踩的坑：`link_mask` 是"上一轮"，而帧尾 `polled_cnt` 是"本轮"。**

端口任务每轮开头把 `runtime->link_mask` 清 0、逐台应答成功才置位，但**只在整轮结束时**才回写
`SerialDataBuf[7..10]`（[User/main.c](../User/main.c) 里 `uart_published_link_mask()` 上面那段注释
解释得很清楚：中途发布"半成品"会让每轮里靠后的模块被随机判离线）。
而 `uart_polled_cnt[port]` 是**本轮已经问到第几台**，每轮从 module 0 重新计数。

所以同一帧里这两个数**天生差一拍**，这不是 bug，是刻意的：

| 现象 | 含义 |
|---|---|
| `link=0` 且 `polled_cnt=0` | 本轮**一台都没问** → 该端口所有模块都处于跳过态（连续失败 ≥3 次后每 10 轮才探一次）→【粘住】，不是新故障 |
| `link=0` 且 `polled_cnt>0` | 真的问了这么多台却一台都没答 →【真故障】 |
| `polled_cnt == 该端口模块数` | 本轮全量轮询，没有模块被跳过（正常态，也是抓帧最容易碰到的时刻） |
| `link` 全在线但 `polled_cnt` 很小 | 本轮刚跑到一半，上一轮是好的 → 正常 |

> 例外：刚上电（`uptime` 只有几秒）时 `polled_cnt=0` 不是"粘住"，而是**端口任务还没跑完第一轮**
> （见 2.5 的 `uptime` 一条）。收端工具在 `uptime < 15s` 时会直接标注"刚上电/首轮还没跑完" ——
> 注意这条**只对 v42 及更早**成立，v43 起上电时 `link` 直接按"全在线"填（见 §1.5）。

**v43 起还要多记两条**（v44 把第 1 条的门限换了，见下）：

* `link_mask` 是**去抖后**的结果：离线位要**连续 5 轮失败**（v43）/ **静默 ≥2s**（v44 起，
  见 §1.6）才清 0（v42 及更早是"本轮失败就清"），所以单次丢应答不会再在帧里留下痕迹；
* 反过来，真拔掉一台模块，也要到判决条件满足才会看到它的位变 0（v43 最坏 ≈30s，**v44 约 2s**，
  **v45 约 2~3.5s** —— v45 把"判决当场发布"撤回成"每轮末尾发布"，见 §1.6b）——
  别把它当成"报警不灵了"。

**v45 起这个掩码只在每轮末尾更新一次**（v44 曾经在判决当场就回写，v45 撤回了）：所以帧里的
`link_mask` 永远是**上一轮跑完的完整结论**，不存在"轮内半成品"。串口7 读它驱动蜂鸣器/报警灯，
和上位机拿到的模块数据帧是同一轮、同一份 —— 两者**一起变**，不会出现"本地报警了、上位机还正常"。

### 2.4 状态量 `[5..13]`

| 偏移 | 变量 | 来源 | 判读要点 |
|---|---|---|---|
| [5] | `s_local_board_alarm` | 本板判决 | = 维度1（任一端口 `link != expected`）或 维度2（任一在线模块 KGL）。**L=1 时一定要看端口块**，它只告诉你"有事"，端口块才告诉你是谁 |
| [6] | `s_remote_board_alarm` | 第7路 FC03 读从机通信板 | 要和 [13] 一起看，见下 |
| [7] | `s_io_cut_switch` | IO 模块 FC02 读 DI0 | FC02 连续超时 15s 后**强制置 0**（不然会拿一个僵尸值去驱动真值表） |
| [8] | `s_io_break_switch` | IO 模块 FC02 读 DI1 | 同上 |
| [9] | `s_buzzer` | 报警真值表 → DO1 | 真值表输出，不是原始输入 |
| [10] | `s_alarm_light` | 报警真值表 → DO2 | ⚠ `= 报警 \|\| 断接 \|\| cut`，**cut 是操作员按下的动作**，所以"报警灯亮"不一定等于"有报警" |
| [11] | `s_work_light` | DO0 | = 上位机 TCP 连接状态（`client_is_connected()`） |
| [12] | `s_io_comm_fail_cnt` | IO 模块 FC02 连续失败 | **>0 时本帧的 [7]/[8] 不可信** |
| [13] | `s_slave_read_fail_cnt` | 第7路 FC03 连续失败 | 每次成功清零，所以 `[13]=38` = 到这一帧为止已连续失败 38 轮（第7路一轮约 500ms → 约 19s） |

`[6]` 的三种情况（这是最容易误判的一条）：

| 现象 | 结论 |
|---|---|
| `[6]=1` 且 `[13]=0` | FC03 **读成功**且从机板返回了 1 → **从机板真的在报警**，去查从机板自己那台 |
| `[6]=1` 且 `[13]>0`、`err=8 (ETIMEDOUT)` | 从机**根本没应答** → 查 addr1 那一侧：从机栈没跑 / 地址不是 1 / 收发器或方向控制。（同总线上的 IO 模块是好的就说明总线本身没问题） |
| `[6]=1` 且 `[13]>0`、`err=3 (EPORTERR)` | 应答来了但帧坏了（CRC 错）→ 方向控制时序 / 总线冲突 / 干扰 / 两端波特率不一致 |

主机模式 [5][11] 全部有效；从机模式只有 [5] 和 [11] 有效，其余恒 0。两块板发的是同一种帧，靠**源 IP** 区分。

### 2.5 帧尾诊断量

| 字段 | 宽度 | 说明 |
|---|---|---|
| `s_slave_last_err` | 1B | 最后一次 FC03 的 `eMBErrorCode`（见下表） |
| `uptime` | 2B LE | `HAL_GetTick()/1000` 的低 16 位 = **上电至今秒数**（65536s = 18.2 小时回绕一次） |
| `WTD_RESET` | 1B | 看门狗复位码，**0 = 此刻没判要复位**（≠ 从未复位过） |
| `polled_cnt × n` | nB | 每个端口"本轮已发起请求的模块数"，顺序与端口块一一对应 |

`eMBErrorCode`（`err_name()` 的表）：

| 值 | 名称 | 含义 |
|---|---|---|
| 0 | OK | 成功 |
| 1 | ENOREG | 非法寄存器地址 |
| 2 | EINVAL | 非法参数 |
| 3 | EPORTERR | 应答帧坏 / CRC 错 |
| 4 | ENORES | 资源不足 |
| 5 | EIO | IO 错 |
| 6 | EILLSTATE | 协议栈状态异常 |
| 7 | EAGAIN | 需重试 |
| 8 | ETIMEDOUT | 从机没应答 |

#### `uptime`：最直接的"板子有没有在复位"判据

同一块板的**两帧之间这个值变小 = 板子重启过**（`18.2h` 回绕也表现为变小，用"旧值很大、新值很小"区分）。
为什么重要：端口任务要等配置从网口下发完才开始跑，而任务启动时会把 `link_mask` 清 0 ——
而任务启动时（**v42 及更早**）会把 `link_mask` 清 0 ——
所以那些版本**每次复位都会重演一遍"所有端口全掉线"的报警**，看着像总线故障，其实只是刚上电。
**v43 起没有了**：上电时 `link_mask` 直接按"全在线"填（见 §1.5）。
收端工具检测到变小时会直接打一行 `<-- 板子复位过!`，并把上一帧的复位码点出来。

#### `WTD_RESET`：复位码全表

复位码是**普通的 RAM 变量**，复位后初始化就清零了 —— 所以它只可能出现在"复位前那最后一帧"里，
这是为什么要有 v41 那个"判定要复位就无视报警门槛补发一帧"的机制（见第 1 章）。

| 码 | 含义 | 触发条件（[User/main.c](../User/main.c) `App_TaskStart`，500ms 一轮） |
|---|---|---|
| 0 | 无 | 正常 |
| 1 | 配置变更 | 收到上位机配置帧 |
| 2 | 上位机软复位命令 | 收到软复位命令 |
| 21~26 | 串口任务卡死（端口 1~6） | `WDTUARTFLAG[i] > 500` → **250s** 没喂狗 |
| 27 | 心跳超时 | `heartbeat > 120` → **60s** 上位机无应答 |
| 28 | TCP 发送任务卡死 | `WDTTCPSENDFLAG > 500` → **250s** |
| 29 | 申请配置帧发送失败 | 控制帧，仍然复位 |
| 30 | 日志帧发送失败 | 控制帧，仍然复位 |
| 31 | **OTA 任务卡死** | OTA 任务 30s 没上报存活（`ota_task_wdt_timed_out()`） |

**废弃码（v40 起不再出现，老固件/老抓包里还会见到）**：`19`、`20+port*6`（=20/26/32/38/44/50）端口
数据帧发送失败；`3+n*2` 奇数码 曲线上传失败。（数据帧发送失败现在只断链重连，不整机复位 ——
原因见 [User/client.c](../User/client.c) `client_add_to_tcp_send_buf()` 上面那段"2026-10-13 收紧"的约定。）

> 数字上值得记一笔：21~26 / 28 的门槛是 250s，27 是 60s，31 是 30s。所以
> **一台"上电才三十几秒就复位、复位码 31"的板子，时间上只可能是 OTA 任务看门狗**。

### 2.6 版本兼容：靠总长就能分区

| 版本 | 帧尾 | 总长公式 | n=5 时 |
|---|---|---|---|
| v36（最老的定长形态） | 干脆没有端口块 | 14 | 14 |
| v37 / v38 | 无 / 只有错误码 1B | 15+13n / 15+13n+1 | 80 / 81 |
| v39 / v40 | 错误码 + 上电秒数 2B + 每端口 1B | 15+13n+3+n | 88 |
| v41 / v42 | 错误码 + 上电秒数 2B + **复位码 1B** + 每端口 1B | 15+13n+4+n | **89** |

四种总长互不相等，所以新旧固件的抓包可以一起丢给收端工具，不会误判；
长度对不上或 magic 不对的包会单独提示，便于发现收发两端版本不一致。

发帧门槛（决定"什么时候能收到帧"）：

* `DBG_LOG_ALARM_ONLY = 1`（v36 起）：**常态静默，只有报警时才发** → 收到一帧 = 这一刻在报警，
  帧与帧之间的空档 = 已恢复。
  *例外*：① 判定要复位时补发的那一帧（v41 起，`dbg_log_udp_send_ex(1)`，无视门槛）；
  ② v42 的 OTA 诊断帧（它有自己的门槛，只受 `g_rs485_7_log_udp_enable` 约束）。
* 节奏：主机每轮 `RS485_7_POLL_DELAY_MS = 500ms`，从机按 `DBG_LOG_SLAVE_PERIOD_MS = 500ms` 限流。

## 三、25 字节 OTA 诊断帧（magic `00 A6 6A 88 9A`，v42 临时）

为什么会临时加这么一帧：v41 之后现场抓到"复位码 31、上电才 34s、而同一帧里 5 路端口全部正常"。
也就是说**系统其余部分都好，只有 OTA 任务 30s 没上报存活**。但"没上报"有两种完全不同的成因，
光看复位码分不出来：

* **(a) 卡在某个调用里出不来** —— connect / send / recv / Flash 擦写；
* **(b) 被饿死** —— OTA 任务是**全系统最低优先级（prio 4）**，而 6 路 UART 和 RS485-7 都是 prio 5；
  只要它们把 CPU 占满，prio 4 一次都排不上，现场表现和"卡住"一模一样。

这一帧就是把 OTA 任务的"生死"搬出来。它跟状态帧共用同一个 socket / 目的地址，跟在一帧状态帧后面发，
约 2 帧/秒（不受报警门槛限制）。

| 偏移 | 字段 | 说明 |
|---|---|---|
| [0..4] | magic `00 A6 6A 88 9A` | 末字节 `9A` 与状态帧的 `99` 区分，收端按 magic 分流 |
| [5..6] | `uptime` LE u16 | 上电秒数 |
| [7] | `stage` | OTA 任务此刻停在哪一步（取值表见下） |
| [8] | `sock_open` | 1 = 当前有 TCP 连接 |
| [9] | `sess` | 0=IDLE 1=DOWNLOADING 2=DONE |
| [10..11] | `left_s` LE u16 | 距"判卡死"还剩几秒；**0xFFFF = 还没 arm（看门狗不判超时）**，0 = 已到点 |
| [12..15] | `report_cnt` LE u32 | OTA 看门狗累计上报次数（只增） |
| [16..19] | `loop_cnt` LE u32 | OTA 主循环累计圈数（只增） |
| [20..23] | `test1_cnt` LE u32 | prio 1 的 `Test1_Task` 累计圈数（"CPU 还有没有空闲"的旁证） |
| [24] | `WTD_RESET` | 复位码，同状态帧 |

`stage` 取值（[User/ota/ota_client.h](../User/ota/ota_client.h) / `ota_client.c`）：

| 值 | 含义 |
|---|---|
| 0 | 还没进主循环（刚创建 / 堆不足没起来） |
| 1 | **循环顶**（不在任何阻塞调用里）← 饿死时会停在这里 |
| 2 | 等重连间隔（`vTaskDelay`） |
| 3 | `ota_net_connect`（非阻塞 + select ≤3s） |
| 4 | 发 HELLO |
| 5 | 会话-上报存活 |
| 6 | 会话-取帧/分发（**Flash 擦写走这里**） |
| 7 | 会话-收网络（select ≤200ms） |
| 8 | 会话-周期 HELLO |
| 9 | 断开连接 |
| 10 | 升级完成等重启 |

判读表（收端工具会直接把结论打出来）：

| 现象 | 结论 |
|---|---|
| `report`/`loop` 在涨，`还剩≈30s` 一直贴顶 | 任务健康，**忽略这一行** |
| `report`/`loop` **冻住** + `stage=1` | **被饿死**：它是最低优先级，被 prio≥5 的任务占住 CPU |
| `report`/`loop` 冻住 + `stage=2..10` | **卡在那个调用里**：查这个调用里的超时/阻塞 |
| 同一现象且 `c1`(prio1 任务)也不涨 | 整机都被 prio≥5 占满，不是单个任务的事 |
| `还剩…` 一路往 0 走 | 正在滑向复位，这一行是"死前自述" |
| `stage=0` 且 `report=0` | OTA 任务**根本没跑起来** → 查 `xTaskCreate` 是否因堆不足失败（它要 4096B，`configTOTAL_HEAP_SIZE` 只有 28KB） |

> 注意 `stage=6` 期间 `report_cnt` 本来就可能一两帧不涨：Flash 擦除/校验是按扇区喂狗的，
> 擦一个 128KB 扇区典型 1.1s，而诊断帧 500ms 一帧。所以"计数器不动"要连续多帧才算数。

```bash
python PC_Server/udp_status_log_listen.py --log run42.txt
```

* 默认**只在内容变化时打印**（否则每 500ms 一行会刷屏）；`-a` 打全部帧。
* 建议带 `--log`：诊断帧冻结的那几十秒轨迹会留在文件里，板子一复位就再也拿不到了。
* 控制台是 GBK，工具已加 `errors="replace"` 兜底，不会因为某个字符编不出来而中断。

抓这一轮复位的步骤：

1. 板子上电，工具跑起来，等它自己复位一次（约 36s）→ 先确认复位码确实是 31；
2. 复位**前**那几秒的诊断帧最关键：看 `stage` 停在哪、`report/loop` 是不是冻住了；
3. 按第 3 章的判读表分流到 (a) 卡在调用里 还是 (b) 被饿死 ——
   如果是 (b)，下一步就是评估给 OTA 任务提优先级（或给 prio 5 的端口任务加让出点），
   而不是继续在 OTA 模块里找超时。
